# C4

## What it is and when to use it {#que-es}

Simon Brown's C4 model describes the architecture of a piece of **software** with four zoom levels, like
a map: the **context** (the system and who uses it), the **containers** (the applications and databases
that make it up), the **components** of each container and, if needed, the **code**. It adds a fifth
**deployment** view (which servers each thing runs on).

Use it to explain a system to a new team, prepare an architecture review or document what talks to what.
It is simpler than ArchiMate and can be read without prior training. If you need to relate the software
to business processes, link it to [ArchiMate](archimate.md).

## Key elements {#elementos-clave}

| Element | Level | What it represents |
|---|---|---|
| **Person** | Context | A human user: "Account manager", "Customer" |
| **Software system** | 1 · Context | Something that delivers value on its own: "CRM". Contains containers |
| **Container** | 2 · Container | An application or data store deployed separately: "Manager portal", "Customer API", "Database". Fields `technology` and `kind` (app, database, queue, browser, mobile, microservice…) |
| **Component** | 3 · Component | A piece of a container with a clear interface |
| **Code** | 4 · Code | A class, interface or module (optional level) |
| **Deployment node** | Deployment | Infrastructure: server, virtual machine, cluster, cloud service. They nest and have `instances` |
| **Boundary** | Any | A dashed frame to group things (enterprise, system, group) |

People and systems have an `external` field: tick it for things outside your scope and they are painted
gray, as C4 prescribes.

## Relations {#relaciones}

| Relation | What for |
|---|---|
| **Relationship** | C4's generic relation. Fill in `description` ("Reads and writes") and `technology` ("JSON/HTTPS", "SQL"). It is the default relation |
| **Uses** | Same as above but with the explicit verb "the source uses the target"; handy when exporting to Structurizr |

## Getting started {#como-empezar}

This is how the demo's C4 view (*CRM · Contenedores*, "CRM · Containers") is built:

1. In the **Views** panel, press **＋** and choose **C4**. In the view's inspector, choose the **Container**
   viewpoint.
2. Drag a **Software system** "CRM" and make it large: it will be the frame that holds the rest.
3. Drag three **Container** **inside** the system: "Manager portal" (technology *React*, kind *browser*),
   "Customer API" (*Node.js*, *microservice*) and "Database" (*Postgres*, *database*).
4. Outside the system, add another **Software system** "KYC provider" and tick `external`.
5. Join portal → API ("JSON/HTTPS"), API → database ("SQL") and API → KYC provider ("REST") with
   **Relationship**.
6. To make the ArchiMate CRM open this view on double-click, go to the ArchiMate view, right-click "CRM"
   → **Open in another dimension**, or choose this view under **View on double-click** in the inspector.

## Notation rules {#reglas}

- **Hierarchy by nesting**: a system contains containers, a container contains components and a
  component contains code. A deployment node contains other nodes and containers; a boundary, anything.
  Nesting creates no relation.
- **Matrix**: almost everything can relate to almost everything, with two exceptions: a person doesn't
  relate to another person, and **Code** only relates to code or components.
- **Viewpoints = levels**: *Context* (people, systems, boundaries), *Container* (adds containers),
  *Component* (adds components), *Code* (adds code) and *Deployment* (nodes, containers and systems).
  Whatever doesn't belong to the level is dimmed in the palette.

## Import and export {#importar-exportar}

- **Structurizr JSON**: import and export people, systems, containers, components, deployment, relations
  and views with positions. Boundaries and the code level are left out with a warning when exporting. See
  the [format table](../importar-exportar.md#formatos).
- Each view can also be exported to SVG, PNG, Mermaid and draw.io.

## Common mistakes {#errores-comunes}

- **Mixing levels in one view**: a context diagram with loose containers is confusing. Use one view per
  level and link them with detail views.
- **Relations without a description**: an arrow with no "what" or "how" explains nothing. Always fill in
  `description` and `technology`.
- **Container ≠ Docker container**: in C4 a container is anything deployed separately (a website, an API,
  a database). Docker containers or servers are **Deployment nodes**.
- **Leaving containers outside their system**: if you don't nest them inside their system, the
  Structurizr exporter puts them under "Sin sistema" (no system).
